# Harness Engineering — 大任务工程化脚手架

## 核心原则

1. **风车而非风**：模型是风，Harness 是风车。不盯着模型够不够强，而是搭好外面的脚手架
2. **轮班工程师**：每个新会话都是"接班"，不知道上一班发生了什么，靠文件交接
3. **生产者和评判者分离**：没有人能批改自己的卷子
4. **重置优于压缩**：上下文快满时，写文件 + 开新会话，比压缩历史更可靠
5. **先最简后加复杂度**：每个 Harness 部件都是对模型短板的假设，模型升级后要砍掉不需要的

## 阶段 0：判断是否启用

收到任务后，先评估：

**启用 Harness 的信号**：
- 用户说"大任务/复杂项目/长时运行/按 Harness 来"
- 任务需要构建完整功能模块（5+ 文件）
- 预计无法在一个会话内完成
- 涉及多个独立功能点的实现

**不启用的信号**：
- 单文件修改、快速 fix、简单问答
- 预计 5 次工具调用内可完成
- 用户明确说"直接做/简单改一下"

**决策方式**：用三岔路口模式，向用户确认。例如：
> "这个任务看起来比较复杂，建议按 Harness 模式（工程化脚手架）来做。要启用吗？还是直接开干？"

## 阶段 1：Initializer（开局）

在项目根目录创建 Harness 工件：

### 1.1 进度日志 `harness/progress.md`

```markdown
# 项目进度日志

## 项目概述
[一句话描述目标]

## 当前状态
- 阶段：初始化
- 上一条完成：无
- 下一步：[第一条任务]

## 会话记录

### Session 1 — [日期]
- 完成：[做了什么]
- 遗留：[未完成什么]
- 备注：[关键决策/发现]
```

### 1.2 功能清单 `harness/checklist.json`

```json
{
  "project": "项目名",
  "created": "ISO日期",
  "items": [
    { "id": 1, "desc": "功能描述", "done": false, "priority": 1 },
    { "id": 2, "desc": "功能描述", "done": false, "priority": 2 }
  ]
}
```

**铁律**：
- 穷举所有功能点，宁可多列
- 编码 Agent 只能把 `false` 翻成 `true`，不许删除或修改条目
- 用 JSON 格式（比 Markdown 更不容易被模型随意改动）

### 1.3 高层规格 `harness/spec.md`

- Planner 角色的输出
- 只管范围和高层设计，不碰太细的技术决策
- 细节定得太死会一层层放大成错误

### 1.4 Git 基线

```bash
git init  # 如果还没有
git add -A && git commit -m "harness: 初始化基线"
```

## 阶段 2：开工仪式（每个会话启动时）

每次新会话接手项目时，必须先执行以下步骤：

1. **确认目录**：`pwd`，确认在正确的工作目录
2. **读进度**：读 `harness/progress.md`，了解上一班干了什么
3. **读 Git log**：`git log --oneline -10`，看最近的提交
4. **挑任务**：读 `harness/checklist.json`，找优先级最高的 `done: false` 条目
5. **确认状态**：如果项目可运行，先跑一遍基础测试确认当前状态正常
6. **开干**：先进入状态，再写代码

## 阶段 3：执行纪律

### 3.1 一次只做一件事
- 每个会话只挑一条 checklist 项来做
- 这样既不会把上下文耗尽，也避免来回切换

### 3.2 做完必留痕
- 写一条描述清楚的 Git commit
- 更新 `harness/progress.md` 的会话记录
- 翻转 `harness/checklist.json` 中对应条目的 `done` 状态

### 3.3 出问题就回滚
- 万一引入 bug，`git revert` 到上一个干净的基线
- 不要在坏的基础上修补

## 阶段 4：评审与验收

### 4.1 独立评审（Evaluator）

**关键原则：生产者和评判者必须是不同的 Agent。**

用 `delegate_task` 派一个子 Agent 做 Evaluator：
- 子 Agent 只看最终产出，不看实现过程
- 按评分标准逐条验证
- 硬指标不达标就判定失败，给出详细反馈

### 4.2 评分标准（按项目类型调整）

通用四维度：
1. **设计质量**：是否连贯的整体，而非组件拼盘
2. **原则性**：有无刻意的自定义决策，而非套模板
3. **工艺**：代码风格、命名、结构是否到位
4. **功能性**：抛开实现细节，功能是否真的可用

### 4.3 验收方式
- 不只跑单元测试
- 端到端验证：像用户一样走一遍完整流程
- 有 UI 的话用浏览器自动化或截图验证
- 功能性验收 = 模拟真实使用场景

### 4.4 迭代
- Generator 收到 Evaluator 反馈后修复
- 通常 2-3 轮迭代（Hermes 场景下比 Anthropic 原文 5-15 轮少，因为任务粒度更细）
- 每轮修复后重新提交评审

## 阶段 5：上下文管理

### 5.1 重置优于压缩

上下文快满时（对话过长、工具输出累积过多）：
- **不要**：试图压缩历史继续扛
- **要**：
  1. 把当前进度完整写入 `harness/progress.md`
  2. 更新 `harness/checklist.json`
  3. Git commit 当前状态
  4. 告知用户"上下文即将用尽，已保存进度，请发'继续'开启新会话"

### 5.2 状态全在文件里
- 对话记忆不可靠（会话结束就消失）
- 所有关键状态必须持久化到文件
- 新会话从文件读回来，等效"重置"但信息不丢

## 阶段 6：瘦身与演进

### 6.1 定期审视
- 每完成 3-5 个 checklist 项后，回头审视：
  - 哪些 Harness 部件是多余的？
  - 评分标准是否需要调整？
  - 开工仪式是否有可简化的步骤？

### 6.2 模型能力变化时调整
- 如果换了更强的模型，可以：
  - 去掉 Sprint 拆分（一次多做几条）
  - 简化评审（减少迭代轮数）
  - 合并 checklist 条目
- 原则：先最简，需要时才加复杂度

## 适用范围提醒

**不要过度工程**：
- 简单任务（单会话可完成）→ 直接做，Harness 是负债
- 探索性任务（不确定方向）→ 先 spike，确认方向后再上 Harness
- 修 bug / 小改动 → 直接改，不需要仪式

**适合 Harness 的场景**：
- 构建完整应用或功能模块
- 大规模代码重构
- 多人协作的长期项目
- 需要跨会话持续推进的任务

## 目录结构示例

```
project-root/
├── harness/
│   ├── progress.md      # 进度日志
│   ├── checklist.json    # 功能穷举清单
│   ├── spec.md           # 高层规格
│   └── reviews/          # 评审记录
│       ├── review-001.md
│       └── review-002.md
├── src/                  # 项目源码
└── .git/
```

## 与 Hermes 其他 Skill 的协作

- **task-logger**：Harness 的会话记录可作为 TaskLog 的输入源
- **writing-plans**：Harness 的 spec.md 可由 plan skill 生成
- **delegate_task**：用于实现独立的 Evaluator 角色
- **cronjob**：长期项目可设置定期进度检查的 cron job

## Pitfalls

- **不要跳过开工仪式**：省那 2 分钟会导致后续浪费 20 分钟在错误的方向上
- **不要让 Agent 自评**：自评总是偏乐观，必须用独立 Evaluator
- **checklist 不要用 Markdown**：JSON 格式更不容易被随意修改
- **commit message 要写清楚**：下一班靠这个理解上一班做了什么
- **不要一次性硬干**：看到 checklist 还剩很多就想一口气做完 → context 耗光 → 翻车
- **进度日志不要写废话**：只写"做了什么、遗留什么、关键决策"，不要写"我正在思考"
